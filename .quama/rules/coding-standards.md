# 编码规范

## 代码简洁性原则

**最好的代码是永远不需要写的代码。**

### 实施方法

1. **问题理解**：在写代码之前，彻底理解问题
2. **方案选择**：选择最简单的解决方案
3. **代码审查**：检查是否有不必要的复杂性
4. **重构控制**：只在必要时重构

### 禁止行为

- ❌ 过度设计
- ❌ 不必要的抽象
- ❌ 复杂的算法（当简单算法足够时）
- ❌ 冗余的代码

## 代码可读性原则

**代码必须易于理解，因为大多数时间花在阅读代码上。**

### 命名规范

1. **变量名**：清晰表达用途，避免缩写
2. **函数名**：清晰表达行为，避免模糊名称
3. **类名**：清晰表达职责，避免通用名称
4. **文件名**：清晰表达内容，遵循项目约定

### 代码结构

1. **函数长度**：不超过50行（不含空行和注释）
2. **类长度**：不超过500行（不含空行和注释）
3. **文件长度**：不超过1000行（不含空行和注释）
4. **嵌套深度**：不超过3层

### 注释规范

1. **必要注释**：复杂逻辑、业务规则、技术决策
2. **避免注释**：代码本身应该清晰到不需要注释
3. **注释格式**：使用标准格式，保持更新
4. **注释语言**：使用中文，简洁明了

## 代码复用原则

**不要重复造轮子，复用已有的解决方案。**

### 复用层次

1. **标准库**：优先使用标准库功能
2. **已安装依赖**：使用项目已安装的依赖
3. **内部工具**：复用项目内部的工具函数
4. **外部依赖**：谨慎引入新的外部依赖

### 复用检查清单

- [ ] 标准库是否有此功能？
- [ ] 项目已安装的依赖是否有此功能？
- [ ] 项目内部是否有类似功能？
- [ ] 是否必须引入新的依赖？

## 错误处理原则

**错误处理必须完整，不能忽略任何错误。**

### 错误处理要求

1. **捕获错误**：所有可能出错的操作都必须捕获错误
2. **记录错误**：错误必须记录，便于排查
3. **用户友好**：错误信息必须对用户友好
4. **恢复机制**：必须有错误恢复机制

### 错误处理模式

```javascript
// 推荐：完整的错误处理
try {
  const result = await riskyOperation();
  return result;
} catch (error) {
  logger.error('操作失败', { error, context });
  throw new BusinessError('操作失败，请稍后重试');
}

// 禁止：忽略错误
riskyOperation().then(() => {});
```

## 性能意识原则

**编写高性能的代码，但不过度优化。**

### 性能要求

1. **算法选择**：选择合适的时间复杂度和空间复杂度
2. **资源管理**：及时释放资源，避免内存泄漏
3. **缓存策略**：合理使用缓存，避免重复计算
4. **并发处理**：合理使用并发，避免阻塞

### 性能检查清单

- [ ] 算法时间复杂度是否合理？
- [ ] 是否有不必要的循环？
- [ ] 是否有内存泄漏风险？
- [ ] 是否有性能瓶颈？

## 安全编码原则

**所有代码必须考虑安全性，不能有安全漏洞。**

### 安全要求

1. **输入验证**：所有外部输入必须验证
2. **输出编码**：所有输出必须编码，防止注入
3. **权限控制**：所有操作必须有权限控制
4. **数据保护**：敏感数据必须加密存储

### 安全检查清单

- [ ] 是否有SQL注入风险？
- [ ] 是否有XSS漏洞？
- [ ] 是否有权限绕过风险？
- [ ] 是否有敏感数据泄露风险？

## 测试编写原则

**测试必须可靠、可维护、有价值。**

### 测试要求

1. **测试覆盖**：关键路径必须有测试覆盖
2. **测试质量**：测试必须可靠，不能有flaky测试
3. **测试维护**：测试必须易于维护
4. **测试价值**：测试必须有业务价值

### 测试类型

1. **单元测试**：测试单个函数或类
2. **集成测试**：测试组件之间的交互
3. **系统测试**：测试整个系统
4. **性能测试**：测试系统性能

## 代码审查原则

**所有代码必须经过审查，审查必须认真负责。**

### 审查要求

1. **审查时机**：代码提交后必须审查
2. **审查内容**：代码质量、安全性、性能、可维护性
3. **审查反馈**：反馈必须具体、可操作
4. **审查记录**：审查记录必须保存

### 审查检查清单

- [ ] 代码是否符合编码规范？
- [ ] 是否有安全漏洞？
- [ ] 是否有性能问题？
- [ ] 是否有可维护性问题？
- [ ] 是否有测试覆盖？

## 重构原则

**重构必须有明确目标，不能为了重构而重构。**

### 重构要求

1. **重构时机**：有明确的重构理由
2. **重构目标**：有明确的重构目标
3. **重构计划**：有详细的重构计划
4. **重构测试**：重构前后都必须有测试

### 重构检查清单

- [ ] 重构是否有明确目标？
- [ ] 重构是否影响其他组件？
- [ ] 重构是否有测试覆盖？
- [ ] 重构是否有回滚方案？
